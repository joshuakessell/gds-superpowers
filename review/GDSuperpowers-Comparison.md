# GDSuperpowers comparison and consolidation notes

Reviewed: October 12, 2026.

## Snapshots and scope

- ChatGPT-side export: `GDSuperpowers-v0.3.1-Review-Bundle.zip`, original 136-file skill package extracted without changing its source.
- Claude-built GitHub repository: `joshuakessell/gds-superpowers`, `main` commit `cdbebc2c23b64755c8b518c52225106298f0e54d`. The repository identifies its package as version 0.1.0.
- GitHub scope inspected: README, SKILL, all mode procedures, installation entry point and installation library, scaffolder, state/evidence validators, state template, package checker/role inventory, selected host adapters, validation report, scenario definitions, S-11 evaluation record, and scaffolder tests. This is not a claim of a line-by-line audit of every repository file.
- No repository changes, installation into the user's account, paid model calls, or live-host evaluations were performed during this comparison.

## Recommendation

Consolidate into the existing GitHub repository. Preserve its Claude-specific behavioral fixes and evaluation records, while retaining the v0.3.1 adaptive interview, Quick Flow, Task-Observer, installation choices, and stronger installer safeguards. Neither implementation should replace the other blindly.

The v0.3.1 package is closer to the latest requested feature set. The GitHub version is a narrower, independently revised implementation with useful reported Claude runtime experience. Its lower version number does not mean its latest commit predates the export.

## Preserve from the Claude-built repository

### Approval provenance

SKILL.md defines an approval as the user approving a specific document they have been shown. It forbids inferring an approval from urgency or a request to skip the gate. S-11 describes an initial failed attempt and a successful rerun after this rule was added.

Carry the intent into Quick Flow without importing unnecessary ceremony: show a compact slice design and implementation plan together, accept an explicit approval of that shown scope, then record the user's actual message reference. Do not demand another approval for each already-authorized edit.

### Explicit mode contracts

references/modes.md states inputs, procedures, outputs, and stopping conditions for 24 modes. This is a useful format to apply to the more feature-rich package. Keep it compact and load only the relevant mode, not every procedure on every turn.

### Reported behavioral feedback

The repository records failures, fixes, baseline behavior, and limitations rather than relying solely on static tests. Preserve those records, especially approval handling, project preservation, simulation labeling, and absolute project roots in dispatch briefs.

The S-11 record says the tests used one-shot general-purpose Sonnet subagents in Claude Code, one repetition per arm. It also says full transcripts remain in the authoring session and are not bundled. The available records are useful evidence summaries, not an independently replayable end-to-end host trace or proof of reliable behavior across models.

### Additional design lenses

Newcomer and Completionist are useful additions for onboarding and collection/unlock satisfaction. Progression, Encounter, and Economy specialists are useful during system tuning. Keep these as optional lenses or bounded roles; do not combine both complete rosters into a mandatory 26-agent council.

## Preserve from v0.3.1

### Interview-led Quick Flow

Retain one-question-at-a-time discovery, prior-answer reuse, primary/supporting genre selection, graphical direction, and the small first playable target. The GitHub start procedure does not implement this complete interview experience.

### Three-record workflow

Keep game.md for direction, next.md for the current increment, and state.json for durable structured state. Use existing authoritative documents through references. Add extra documents only when a concrete decision or risk justifies them.

### Task-Observer and installation choice

Keep the separate companion, preservation of the previously installed observer, one capture owner, deduplication, optional existing-state storage, and staged skill improvements with separate installation approval.

Keep the repository/global automatic-versus-manual installation question, manual invocation `/gdsuperpowers observe`, repository override of global defaults, saved startup prompt, and optional selected-host prompt submission. Configuration, prompt submission, and actual initialization must remain different statuses.

### Stronger installation checks

Keep backup receipts, recognized-version hashes, conflicting-customization refusal, destination rechecks, exclusive file creation, and symlink checks. These are code-level safeguards, not just instructions to an LLM.

### Evidence research and original player lenses

Retain the separate mechanics and AI-assisted-production tracks, claim-level evidence, unknown outcomes, counterexamples, and bounded research stop rule. Keep Combat Specialist, Build Alchemist, and Explorer explicit when assessing moment-to-moment play and run variety.

## Confirmed installer findings

The inspected GitHub install library was reconstructed locally from the connector response and verified against GitHub blob SHA-1 `b1cb9142b032d515992f453db95407f1d049f998` before executing these bounded probes. No source changes were made to the library. All writes were restricted to disposable local fixtures.

### Finding 1: a stale create plan overwrites a subsequently created file

In `scripts/lib/install.mjs`, `planInstall` records the destination as `create`. `applyInstall` later trusts that action and calls `writeFileSync` without exclusive creation or a fresh existence check. A different writer creating the file between those calls has its content overwritten.

Observed: GitHub version overwrote the fixture file. v0.3.1 `applyManaged` refused the changed destination and preserved the file.

Fix: recheck the batch and use exclusive creation (`flag: 'wx'`) for creates. Retain explicit handling for partial application and concurrent changes. This test does not imply complete filesystem transaction safety in the v0.3.1 installer.

### Finding 2: the selected project root can itself be a symlink

GitHub `hasSymlinkComponent` stops walking when it reaches the selected root, so that root is not checked. A symlink supplied as the project root is followed during installation.

Observed: GitHub version wrote through the symlink; v0.3.1 refused that selected symlink root. This establishes a mismatch with the repository's blanket no-symlink claim, not that every symlinked workspace is inherently unsafe.

Fix: explicitly check the root and relevant path components, or adopt a deliberate documented realpath policy with a validated boundary. Do not advertise a stronger guarantee than implemented.

## Additional source-review concerns

### Concurrency configuration is not validated by the GitHub budget helper

`templates/project-state.json` sets `agentBudget.maxConcurrent`, but `validateAgentBudget` in `scripts/lib/core.mjs` checks per-mode dispatch counts and does not read `maxConcurrent`. The prose still instructs the agent to respect the cap; the gap is missing machine verification, not proof that a particular run exceeded it.

Model active/completed/cancelled job status and check the active count against the configured cap. Validate configuration types and boundaries as well.

### Codex portability needs a real host test

The main GitHub startup wording is centered on `Agent`, `Skill`, `Bash`, and `superpowers:*`. Those are Claude-oriented assumptions. Discover capabilities by function and adapt to the actual host rather than requiring those literal names.

The inspected Codex technical-lead adapter pins `gpt-5-codex`. Availability was not established in this review. Prefer inheriting a selected supported parent model or explicitly validating a user-selected override. Current OpenAI documentation describes parent model/reasoning inheritance when the custom agent omits those overrides.

### Source and evaluation documentation need synchronization

GitHub README's status says live Claude/Codex behavior evaluations are not represented as completed, while VALIDATION.md reports actual Claude installation and scenario runs. Clarify completed Claude checks versus untested Codex and end-to-end game workflows. Do not label the whole system production-proven from the reported single-repetition scenarios.

## Migration hazards

The two skills have different discovery names but both target `docs/gds/state.json`.

GitHub's state uses `schemaVersion`, `phase`, `agentBudget`, and APR records. The review bundle's quick state uses `schema_version: 2`, `milestone`, `answers`, `loop`, `limits`, and revision-aware approvals. The bundle also has its own earlier snake_case schema-1 format. Its legacy support does not automatically recognize the Claude camelCase schema.

Do not install both as independent coordinators over one project. Do not assume the recognized v0.1.0 upgrade baseline accepts the separately authored GitHub source. Do not infer approvals, evidence, or completed milestones while migrating.

Choose one canonical skill identifier and supply thin aliases for existing commands, including `/gdsuperpowers observe` and `/start`. Choose one canonical state schema and implement an explicit, backed-up migration that preserves unknown information and source references.

## Recommended consolidation order

1. Pin both inputs, retain Git history, choose the canonical name and state schema, and specify migration tests.
2. Carry over Quick Flow, the adaptive interview, conditional genre routing, and the complete observer installation behavior without replacing the game's current decisions or code.
3. Port the Claude approval wording, mode-contract format, relevant optional lenses, dispatch-context improvements, and existing evaluation records.
4. Use the stronger installation primitives; add the reproduced edge cases and missing concurrency checks to regression coverage.
5. Run repeatable Claude and Codex smoke tests for discovery, resume, automatic/manual observer behavior, one real specialist dispatch, an approved tiny edit, and an attempted unapproved scope change. Retain redacted raw tool traces, fixture versions, exact prompts, and repeated results where practical.

Success should be measured as correct behavior with fewer user interruptions and bounded context, not the largest agent roster or highest count of Markdown files.
