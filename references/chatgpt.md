# ChatGPT execution boundary

Use this procedure when GDS is selected in ChatGPT or when no authoritative repository filesystem is available. It adapts the same coordinator, not a second skill or project schema.

## Discover capabilities before assuming a workspace

Use the installed skill picker or `@gds-superpowers` when the surface supports it. Otherwise the user's explicit request to follow the supplied skill starts an instruction-only session. A typed `/start` is not proof that ChatGPT registered a slash command. Load packaged references with the actual file or skill-reading tool; resolve their paths relative to this skill, not a guessed local clone.

Read the supplied or connected game brief, state and current work first. A connector repository ID and revision are valid source identities; they are not local absolute paths. If no repository filesystem is accessible, use **conversation planning**: preserve choices, source messages, assumptions, current scope and the next question in the conversation. Do not invent a project root, execution ID, approval record or completed migration. Missing tools must not stop ordinary discovery or design.

Use the same dynamic suggestions and custom-input contract in [interaction](interaction.md). Numbered Markdown is the default when no usable native question tool is exposed. Never submit Claude's `AskUserQuestion` payload to a different host. Preserve custom qualifications, explicit free-form preference, scoped approvals and human playtest gates.

## Work and persistence

Connected reads and explicitly authorized writes may use their actual connector contracts. Report the exact file/revision changed. Without a supported write, provide a clearly labeled **unsaved handoff**; do not claim that a Project, repository or account was updated. A sandbox file is not an installation on the user's computer. An export is a snapshot, not automatic synchronization.

Only use repository lifecycle helpers when a real authoritative checkout, shell and permissions exist. Follow the existing ownership, migration and verification procedures then. Otherwise keep discussion and proposed tasks separate from dispatched jobs. Real subagents require an actual dispatch tool and receipts; sequential viewpoints are not independent Claude or Gemini reviews. Do not create a second state file to work around inaccessible records.

## Observer

A ChatGPT sandbox's home directory is not the user's home directory. Do not run local-global discovery there to conclude that the user's global observer is absent. Inspect the available skill registry or supported connected installation first. If a global observer is visible and compatible, hand off once on an eligible explicit request. If its location or capabilities are not accessible, leave GDS-owned capture off and report **observer availability unverified**. Do not create a second log, reinstall a companion, or enable automatic observation to compensate. Actual local installations retain their existing global-provider precedence.

## Transfer to implementation

Summarize the approved direction and slice with their actual message references, proposed tasks, constraints, checks not yet run and one next action. When an implementation environment becomes available, inspect its existing records, reconcile the handoff and use the recorded approval when verifiable. Do not replay answered questions. Importing a handoff does not itself approve installation, migration, spending, merge or release.
