# Release and controlled improvement

Use upstream verification and branch-finishing procedures. Build success, source integration, and public release are separate actions with separate evidence and permissions.

Confirm target-platform build/export, startup, settings, input remapping where planned, readable menus, save compatibility/recovery, run completion, death/banking, no critical blockers, and relevant performance measurements. Inspect the actual output artifact, not just an exit message.

Audit asset provenance, credits, packaging, dependency versions, known issues, and store claims. Platform availability statements must match real tested/distributable targets. Use current official platform rules for distribution decisions; do not rely on this skill for fixed policy text.

Use actual gameplay captures or clearly labeled mockups. Never imply independent reviews, revenue, certification, or human testing that did not occur.

Prepare a release proposal identifying artifact location/hash, evidence, remaining risks, rollback or save migration considerations, and the exact publication destination. The user must approve publishing, uploading to a store, spending, or destructive cleanup. Do not commit/push/merge beyond existing explicit authorization.

After release, categorize feedback into defects, readability, balance, progression, and new content. Diagnose before patching, validate improvements, and check requests against pillars and scope. Treat sales and retention data as evidence only when actually available and properly defined.
